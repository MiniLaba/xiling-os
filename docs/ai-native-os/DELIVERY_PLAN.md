## V0 — 目标冻结与新旧隔离（历史完成；新目标需重新验收）

- 建立本规格、目标架构和机器可读产品清单。
- 区分冻结 Web 科研 OS、桌面壳试验和当前 AI Native Virtual OS。
- 门禁检查禁止活动代码导入冻结旧版。

验收：新开发者只阅读根 README、`xiling.product.json` 和本目录即可说清产品公式、事实所有权及非目标。

## V1 — 身份、工作与记忆边界（进行中：Session 实体与目标归属已完成）

- 补全 Agent、Session、Task、Context、Memory、Workspace 的独立实体与生命周期。
- 所有目标必须进入 Session 和 Task；Session 不等于聊天历史，Memory 不由聊天自动堆积。
- 事件重放后身份、Session、任务和关联关系一致。

验收：同一 Agent 可有多个 Session；Task 可追到所属 Session；不同 Agent 无法读取彼此 Memory。

## V2 — Main Agent 目标闭环

- 桌面默认入口改为 Goal Composer 和 Decision Inbox。
- Main Agent 将目标、约束与“必须确认的动作”编译为可恢复 Task。
- Chat 仅作为人与 Main Agent 的连续入口，不承担系统真相。

验收：用户不选择 App/角色即可完成一个真实小任务；重启后可继续；需要授权时必停。

## V3 — 动态能力与 AI Native App

- 能力目录常驻轻量元数据，命中后才加载 Plugin/Skill/MCP 详情。
- 用 `Agent + Memory + Plugins + Workspace + Generative UI` 形成任务期应用实例。
- 能力卸载后释放资源；第三方供应链通过签名、权限差异和回滚门禁。

验收：两个不同目标由同一通用 Agent 装配出不同能力集合，未命中工具不进入 Context。

## V4 — 隔离多 Agent 与 A2A

- 只在并行收益、权限隔离、上下文冲突或专门环境确有必要时创建 Worker。
- A2A 支持委托、进度、输入请求、取消和 Artifact 返回。
- 权限只能衰减，不能因委托升级。

验收：Worker 无法读取 Main 私有 Session/Memory；交付包可审计且显著小于源 Session。

## V5 — 可信生成式界面

- 建立组件注册表、schema、动作协议和生命周期。
- Decision Inbox 聚合所有等待人类的选择、审批和授权。
- UI 由任务状态决定，不由固定页面流程决定。

验收：比较、表单和审批三类任务确定性生成对应 UI；恶意组件与过期动作被拒绝。

## V6 — 安全、恢复与资源预算

- Harness/工具/插件运行在明确隔离边界；高风险动作审批与幂等。
- 崩溃恢复、取消、超时、凭据隔离和跨平台安全适配。
- 冷启动和空闲资源预算成为发布门禁。

验收：模拟崩溃不产生假完成和重复副作用；空闲不常驻模型、索引或 Worker。

## V7 — 应用生态与发布

- 提供声明式应用 SDK、受信 UI SDK、Plugin/Skill/MCP 适配规范。
- 科研、办公等能力作为领域包安装；海洋科学只是可选包。
- 完成签名、更新、备份恢复、SBOM 和三平台真机验收。

## 每阶段防偏离检查

1. 是否让用户更接近“表达目标”，还是又要求用户学习固定页面？
2. 是否把长期身份、一次 Session、即时 Context 和长期 Memory 混在一起？
3. 是否加载了当前任务不需要的能力或历史？
4. 是否把固定职业角色写进内核？
5. 是否让 UI 成为事实源或执行任意模型代码？
6. 是否把完整 Session/Workspace 交给另一个 Agent？
7. 是否仅做了可见界面，却没有真实任务、权限、恢复和 Artifact 闭环？
